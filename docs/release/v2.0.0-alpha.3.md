# ir-lang v2.0.0-alpha.3: negative `pow` exponents follow OPS

**A pre-release of the 2.0 redesign, and a conformance fix.** alpha.2 disagreed with the
family's operation semantics on one case. alpha.3 fixes that case, re-checks the rest of OPS v2
for the same kind of drift, and corrects the IR spec to match. It changes no other behaviour.
The normative specs are `_lexersketch/specs/OPS.md` v2 and `_lexersketch/specs/IR.md`, now
v2.1.

It is still an alpha (D18). 2.0.0 follows once the HIR lowering, the optimizer and instruction
selection have used it end to end.

## What changed in 2.0.0-alpha.3

### Integer `pow` with a negative exponent (ISSUES P36)

OPS v2 says that integer `pow` with a negative exponent is the `NegativeExponent` error (E0006)
under every `overflow` policy except `promote`. Two sections are normative: the `pow` row of §3
and the E0006 row of §6. alpha.2 and IR.md v2 made it a trap with code 6 under
`overflow = trap`. bvm-lang raises the error, so irgen-lang 0.2's bytecode differential found
the two tiers disagreeing. irgen worked around it by testing the exponent itself before the
operation.

alpha.3 follows OPS:

- `BinaryOp::can_error(policy, ty)` is `true` for **every** signed integer `pow`, `trap`
  included. On a signed type, `pow<overflow=trap>` is valid only as the operation of a `check`
  terminator. As a plain instruction, the builder and the validator refuse it with
  `ErrorOutsideCheck`. A `check` of it is now accepted; alpha.2 refused it with `NotFallible`.
- The interpreter and `eval_binary` return `OpFault::Error(NegativeExponent)` for a negative
  exponent under every policy. A `check` therefore takes its error edge with `err = 6`.
- `overflow = trap` still traps with code 1 when the power does not fit the type. It covers
  overflow only. It never turns the negative-exponent error into a trap.
- On unsigned types nothing changes: no exponent is negative, so `pow<overflow=trap>` is still a
  plain instruction that can trap on overflow.

The printer and parser needed no change: they handle policies as syntax. `pow<overflow=trap>`
still parses and prints, and `Module::validate` decides whether it is valid for its operand type.

### The rest of OPS v2, re-checked

The other policy cases were checked against the interpreter and IR.md for the same kind of
drift:

- `shift = saturate` with a negative amount or an amount past the width;
- `shift = mask` with a negative amount;
- `div_zero`;
- signed `MIN / -1` and `MIN rem -1`;
- `float_to_int` under `error` and `saturate`;
- `int_cast`;
- `neg` and `abs` of `MIN`;
- `char_from_u32`.

None of them diverges. After the fix, only two policies trap: `overflow = trap` (code 1) and
`div_zero = trap` (code 2). That is what OPS defines.

Some documentation had drifted and is now fixed:

- `ValidationErrorKind::ErrorOutsideCheck` listed only `error` fields and `char_from_u32` as
  fallible. That had been stale since alpha.2.
- `OpFault::Error` said "the policy is `error`".
- The installation snippet in `docs/API.md` still named alpha.1.

### IR.md v2.1

The spec is corrected in five sections: §4 (the placement rule), §5 (`pow`), §7 (the `trap code`
row now says that no instruction traps with code 6; a `trap 6` terminator in an error block can),
§8.1, and §16 (the version history).

## How it is tested

- A new test, `test_pow_negative_exponent_rule_for_every_policy_and_signedness`, runs every
  `overflow` policy against every integer type, 24 cases in all. For each case it pins three
  things:
  - `can_error`;
  - the builder's placement both ways (a plain instruction refused, a `check` accepted, and the
    reverse);
  - the interpreter's result for an all-ones exponent. On signed types that is the E0006 error.
    On unsigned types it is the largest exponent, which overflows according to the policy.
- The reference comparison of integer `pow` over every type, policy and OPS edge value now
  expects the E0006 error for every negative exponent.
- The end-to-end test runs a signed `check pow<overflow=trap>` (error edge with code 6, trap 1
  on overflow) and a plain unsigned `pow<overflow=trap>`.
- The differential tests' independent evaluator follows the corrected rule. The random-program
  generator chooses plain or `check` with `can_error`, so signed `pow<overflow=trap>` now takes
  the `check` path.
- Gate: fmt; clippy on stable, 1.99 and MSRV 1.85; tests and docs on Windows.

## Breaking changes and migration

- **A signed `pow<overflow=trap>` must be a `check`.** Before alpha.3, this plain instruction
  was valid:

  ```text
  v2: i32 = pow<overflow=trap> v0, v1
  ```

  Write it as a `check` instead:

  ```text
  check pow<overflow=trap> v0, v1 to b1(res0) error b2(err)
  ```

  The error block receives `err = 6`. To abort with that code, end the block with `trap 6`.
- **`OpFault::Trap(NegativeExponent)` is gone.** The result is now
  `OpFault::Error(NegativeExponent)`. A constant folder can fold the `check` to a `jump` to its
  error block that passes the constant 6.
- Code that chooses between a plain instruction and a `check` should call
  `op.can_error(policy, ty)`. It already gives the new answer.

`CHANGELOG.md` → 2.0.0-alpha.3 has the migration table.

## Not in this release

- No crate lowers HIR into ir-lang 2.0 yet, and no backend reads it.
- opt-lang 0.2 and backend-lang 0.3 pin `=2.0.0-alpha.1`. Moving them to alpha.3 is ISSUES P37.
  irgen-lang can drop its exponent pre-test once it depends on alpha.3.
- There is no SSA updater for definitions that already exist. Vector types are still reserved.
